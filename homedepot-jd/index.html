What this role actually is

Read closely, this is a quality-architecture brief inside a data product: own the test automation suite, design test plans that keep delivery quality consistent across web and mobile, and make defects so well documented that resolution is fast. It also asks for judgment the posting can’t list: which surfaces carry the most decision weight, what coverage against acceptance criteria actually means, and how mobile quality survives real devices and OS fragmentation. Every one of those is a call I already make — in public, with receipts.

01

Baseline before verdicts.

Define the acceptance criteria and the test data first, apply them identically to every target, and let the results argue. A verdict nobody can re-run is an opinion.

02

Defects are documents.

A defect report is a document someone else has to act on. Evidence, reproduction, expected versus actual — written clearly enough that escalation is a decision, not a debate.

03

Regression is a promise kept.

Every fixed failure becomes a test that runs after every change. Post-release verification on real hardware, because users should never be the test report.

Claim Checker — a QA methodology with independence rules

A two-validator verification protocol for AI-generated claims: falsifiable claim atoms, evidence ledgers, independence-grouped validation — including a validator slot deliberately left empty, because a system cannot validate its own output — plus right-of-reply and corrections standards. The Ground News audit (16 claims, two independent validators, cleared with exceptions) is the method running in public; the product page is at claimchecker.teambotics.app.
